# Tabigraphy 学習計画

作成: 2026-09-03 / 決定方法: `/grill-me` による設計インタビュー（Q1–Q22）

Tabigraphy は動くアプリであると同時に、**学習の器**である。この文書は「何をどの順で
学ぶか」と「なぜその順なのか」を残す。数週間後に「なぜ Go-BFF が5段目なのか」を
思い出せなくなったとき、ここが答える。

理解の甘さや答え合わせの記録は**ここには書かない**。それは別管理の learning-log に
隔離してある。分けたからこそ、どちらも正直に書ける。

---

## 1. 原則

**学習が勝つ。** 完成とぶつかったら学習を取る。プロダクトを優先すると、慣れた道具で
最短を通るのが常に正解になり、学習の意味が消える。

**ただし動くものを作る。** 各段階で必ず実機で動く状態にする。動かないコードからは
学べない。

**深さを先に、広さを後に。** Android を先に固める。既存資産があるぶん伸びが早く、
何より**比較の基準ができる**。基準を持たずに5つの技術を広く触ると、どれも
「なんとなく動いた」で終わり、SwiftUI を見ても Compose との違いを言語化できない。

**学習範囲は必要が決める。** 最新 API を網羅的に追わない。位置情報アプリを本気で
作れば、Foreground Service の新しい制約、バックグラウンド位置情報の権限フロー、
電池最適化には必ずぶつかる。**壁は最良の教材**であり、リリースノートは違う。

## 2. 手で書くもの / 委任するもの

| 手で書く（学習対象） | 委任する（学びが無い） |
|---|---|
| `shared/` の expect/actual | Gradle / バージョンカタログ |
| Compose UI、Navigation | CI の構築 |
| Service、権限フロー、Glance | テスト**基盤**（実行環境） |
| SwiftUI 画面、Go の handler | 依存更新の調査 |
| **テスト本体** | 自分が書いた後の機械的リファクタ |

**迷ったら手で書く側に倒す。**

強い原則がひとつ: **自分で書いたコードのテストは自分で書く。** テストを書く行為が、
自分の理解の穴を最も正確に暴く。テスト**基盤**は委任、テスト**本体**は手書き。

## 3. 着手順（依存順）

| | 段 | 学ぶもの | この段で動く状態 |
|---|---|---|---|
| **1** | `shared/` を自分で書く + テスト | **expect/actual**、common と platform の線引き、KMP のテスト | 位置情報が流れ、テストが通る |
| **2** | Navigation3 + 画面を増やす | Navigation3、Compose の最新機能 | 地図と履歴を行き来できる |
| **3** | Room 3 で永続化 | KMP の Room、スキーマ設計 | 移動履歴が残る |
| **4** | Glance ウィジェット | Glance | ホーム画面に今日の移動 |
| **5** | Go-BFF + Login | Go、認証、API 設計 | 端末間で履歴が同期 |
| **6** | iOS ターゲット（SwiftUI） | SwiftUI、`shared/` の再利用検証 | iOS で同じ履歴 |
| **7** | Web / TypeScript / Figma | — | — |

### なぜこの順なのか

元の候補リストは**習熟度が高い順**に並んでいた。これを**依存順**に組み替えた。

**1段目に `shared/` を置く**のが要点。ここの設計が以降すべて（Room をどこに置くか、
iOS で何を再利用できるか）を規定する。他人の設計のまま進むと、**6段目で SwiftUI を
やる時に「共有できていない」と気づく**ことになる。

**Go-BFF が5段目**なのは、同期すべき履歴が3段目まで存在しないから。認証するアプリの
中身が無い段階で BFF を建てても、繋ぐ相手がいない。

## 4. `reference/agent-location-tracking` の扱い

エージェントが書いた位置情報基盤 484行が、参照専用ブランチとして残してある。
**これは正解ではなく、比較対象である。**

- `composeApp/` の 287行（Compose / Foreground Service / 権限フロー）は**取り込む**。
  Android の基礎知識は既にあり、書き直しても学習効率が落ちる
- `shared/` の 191行（expect/actual）は**取り込まず、自分で書く**。KMP は未経験で、
  ここが1段目の学習対象そのもの
- 自分の API 設計が変われば `composeApp/` 側も自分で直す。**設計変更が呼び出し側に
  波及する感覚**まで込みで学ぶ

なお参照版の「動作確認レポート」に含まれるスクリーンショットは、**地図が描画されて
いない状態**（MapTiler の API キーが空）で撮られている。参照版が検証済みの正解では
ないことの実例。

## 5. 到達の判定

各段の締めに、この順で確認する。

1. **動く** — 実機で動作する（最低ライン。目的ではない）
2. **説明できる** — なぜこの API か、代替は何か
3. **優劣を論じられる** — 自分の版と参照版の diff を読み、**どちらが良いかを理由つきで
   言える**（自分の勝ちなら勝ちと書く）

3 が本命。自分の中で完結する 2 と違い、**判断基準を持っているかがそのまま出る**。

**テストは1段目から、ユニットテストで始める。** `LocationTracker` は Android API に
密着していて、素直に書くとテストできない。そこで初めて「なぜ interface を切るのか」
「なぜ Flow を返すのか」が腹落ちする。**テストの勘所は、書き方ではなくテスト可能な
設計から来る。**

## 6. レビューの約束

区切りごと（クラス1つ、テスト1本）に受ける。原則は **答えを言わない**。

| | 対応 |
|---|---|
| コンパイルエラー、ビルド設定、環境 | **即答する。** 学習対象ではなく障害物 |
| 「どこを読むべきか」 | **答える。** ドキュメントの節を名指し |
| 「どう設計すべきか」「どう分けるべきか」 | **答えない。** 問いで返す |

分ける基準は **「それを自分で通り抜けることに意味があるか」**。Gradle のバージョン
不整合を自力で解いても KMP は分からない。

### 詰まったときの脱出

**15分、または同じ発想を3回試したら手を止める。** そこで判定するのは「聞くかどうか」
ではなく「**進んでいるか、回っているか**」だけ。

- **進んでいる**（1回試すごとに仮説が1つ消えている）→ 制限なしで続行。学習はここで起きる
- **回っている**（同じドキュメントを読み直し、同じ発想の変奏を試している）→ 段階を
  1つ上げる（読む場所 → 詰まりの構造の言語化 → 答え）

時間ではなく状態で測るのは、時間が集中度で伸縮するのに対し「同じアプローチを3回」は
客観的に数えられるから。そして判断が「降参するか」ではなく「状態はどちらか」になるので、
自尊心の問題になりにくい。

**15 という数字は暫定である。** §9 で詰まった時間を記録するので、2〜3段も進めば
「自分が実際に何分で回り始めるか」の実データが出る。**その時点で 15 を捨てて実測値に
置き換えること。**（loop-console でも `MAX_TURNS_CAP` を旧データ由来の 15 から実測値
120 に直した。推測で置いた数字は、実測が来たら捨てる。）

## 7. CI と公開

**リポジトリは public にする。** Actions の実行時間が無制限になり（private の無料枠は
月2,000分で、Android ビルドはすぐ食う）、人に見られる前提で書く圧力も学習に効く。
機密混入が無いことは確認済み。

**CI は1段目を書く前に整備する。** 契約は結果を見る前に固定するから意味がある。
書いた後に足すと、既存コードが通るように基準を緩めることになる。

最小構成で始める: `assembleDebug` が通る / ユニットテストが通る / ktlint が報告する。

**autofix は入れない。** `ktlintFormat` のような自動修正を入れると「なぜそれが慣用的で
ないのか」を考える機会が消える。**指摘だけさせて、直すのは自分。**

**AI の PR レビューは、自分でレビューを書いた後に開封する。** 先に読むと答えを
見ることになる。後から開けば見落としが一覧で出るし、「AI が指摘したが自分は不要と
判断した」項目が出れば、それは判断が育っている証拠になる。

## 8. 委任タスクの定型

周辺作業は `agent-queue`（`~/dev/loop-console`）に投げる。3つを必ず守る。

1. `-C ~/dev/tabigraphy`、契約は `./gradlew :composeApp:assembleDebug` が通ること
2. **学習対象ファイルに触らせない制約を prompt に明記する** —
   「`shared/` と `composeApp/src/main/kotlin/com/tabigraphy/` 配下、および `*Test.kt`
   は変更しない」。契約では防げない（ビルドは通ってしまう）ので、制約文で縛るしかない
3. タスク終了後、worktree を必ず片付ける。放置すると親リポジトリのブランチが
   掴まれたままになる（実際に `feature/location-tracking` で起きた）

**2番目が、委任が学習を侵食しないための唯一の防壁になる。**

## 9. 弱点を見つけて強化する仕組み

§1〜§8 は「学ぶ順序」を決めている。ここは「**やってみて分かった弱点を、次にどう
反映するか**」を決める。

これが無いと、learning-log は書かれるが読み返されず、着手順は最初に決めた通りに
進むだけになる。loop-console にも同じ穴があった（個別タスクは見るが集約する層が無い）。
`retro-weekly` を作って埋めたのと同じ構造を、ここにも置く。

### 検出 — 何を弱点の証拠とするか

diff 比較・lint・AI レビューに加えて、**これまで流れて消えていた2つ**を記録に加える。
learning-log に次の2行を足す。

```
- 詰まった箇所と時間: <どこで何分。15分で手を止めたか、そのとき進んでいたか回っていたか>
- 設計で聞きたくなったこと: <問いで返された質問と、最終的に自分が出した答え>
```

後者が最も効く。**問いで返された箇所は、自分の設計判断が届かなかった地点そのもの**で、
これ以上に正確な弱点の指標はない。

### 集約 — 各段の終わりに横断して読む

段の切れ目で learning-log **全体**を読み返し、**同じ理由で詰まっていないか**を探す。
「`shared/` の設計で詰まった箇所と、Navigation で詰まった箇所は、どちらも
『状態をどこが持つか』の判断だった」— これは**並べて初めて見える**。

段の切れ目を選ぶのは、そこが次の段の計画を立てる直前だから。「前回と同じ理由で
詰まったか」を、**次に進む前に**知るのが効く。学習の進み方は不規則なので、
時間で区切ると空振りする。

エージェントの役割は**事実を並べるところまで**。何を強化するかは自分で決める
（`retro-weekly` と同じ境界: パターンを surface する、勝手には動かない）。

### 強化 — 達成度で次の段に条件を付ける

§5 の判定3項目のうち、**「参照版との優劣を論じられる」が弱かった段は、次に進む前に
補強を1つ挟む**。

補強の形は **「同じ技術で、別の題材をもう1つ書く」**。1段目の expect/actual が浅ければ、
2段目に進む前に `shared/` にもう1つ platform 依存の要素（時刻フォーマット、権限状態の
取得など）を expect/actual で足す。**同じ技術を2回目に書くとき、1回目に見えなかった
ものが見える。**

依存順そのものは組み替えない。順序を壊すと、1段目の設計が固まらないまま先に進む
ことになり、§3 で順序を依存順にした意味が消える。
